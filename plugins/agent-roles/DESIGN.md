# agent-roles: design

Read this before changing the plugin. It records why the plugin exists, what it must not become, and what was already tried. A change that contradicts a principle or reverses a decision needs the maintainer's explicit approval and a new entry under [Decisions](#decisions).

## Purpose

A Claude Code session that does everything in its own context fills that context with grep output, build logs and dead ends, and stops responding to its user while it works. A subagent that backgrounds its work or promises to wait reports on work that never ran. This plugin gives every agent a role before its first tool call: the top-level session talks to the user and delegates, and each subagent works in the foreground and ends with findings or reports by message.

## Goals

- One role per kind of agent, delivered by a hook, so the rules are in place without the agent loading anything.
- Role files that read correctly on their own, in any order next to other hooks' context, at any nesting depth.
- A dispatcher role, so the human can talk to one session that runs several worker sessions in tmux instead of managing each of them.
- Rules calibrated from one person's experience with this harness, stated with the reason, so a reader can disagree with the reason rather than the rule.

## Non-goals and scope

- **No enforcement.** Nothing blocks a tool call. The `noisy-tools-in-subagent` plugin enforces the delegation of noisy commands.
- **No launching.** The plugin starts no sessions and imports no code from other projects. The dispatcher role launches workers by calling tmux, cc-session-tools and the launcher commands from its role text. A launcher such as cc-auth-switch can put a role into the system prompt; the plugin then stays silent for that session.

## Principles

1. **Injected, not loaded.** A skill has to be loaded, and a subagent that skips it acts unconstrained. The cost is the role's tokens in every agent.
2. **Each role file stands alone.** Hooks from other plugins write on the same events in an unspecified order, so a role never refers to anything outside itself.
3. **The payload decides, never a brief.** No hook payload carries a nesting depth or a parent; `agent_type` is the only value the caller sets that reaches `SubagentStart`. A role is keyed on it, never on what a prompt claims.
4. **Every role file stays under 9,500 characters.** Claude Code replaces a hook's `additionalContext` above 10,000 characters with a short preview and a file path. `make test` fails above 9,500.

## Decisions

| Date | Decision | Reason |
|---|---|---|
| 2026-09-05 | The session gets an orchestrator role, every subagent a worker role, from a plugin instead of `~/.claude/` | Six installer copies drifted apart; plugin `SessionStart` hooks were believed not to fire, which was never tested and is false on 2.1.260 |
| 2026-09-05 | An unknown problem is probed on a small slice, then the same subagent is resumed for the full scope | A subagent handed the full problem runs its first idea against the full scope and fights it for an hour |
| 2026-09-05 | A worker sizes a wait to the job, 2–10 minutes for a pipeline | Fixed sleeps either overshoot a short job or poll a long one too often |
| 2026-09-21 | The worker role splits into `task-worker` and `resident-worker`, picked by `agent_type` through the `resident_agent_types` option | A resident watcher ends its turn only on its stop condition and reports by message, which contradicts the task role |
| 2026-10-09 | The orchestrator quotes the user's request and names every later write in a subagent's first prompt, never "read-only" | The auto mode classifier treats the first prompt as the user's instruction and a later message from the orchestrator as no consent |
| 2026-11-09 | The resident role and its `resident_agent_types` option are removed; every subagent gets the task role | `mr-babysit` and `code-review:watch` moved to `glab-watch` background tasks that report by message, so no subagent stayed resident |
| 2026-11-10 | The resident role comes back, with no resident type by default; the option alone lists them | The removal took the role away from other resident subagents together with its only default user, `glab:mr-watch` |
| 2026-11-17 | A subagent's model is picked by three questions (is the path known, does something catch a wrong result, what builds on the result) over four tiers, haiku to fable | "Subtask complexity" was vague. Haiku is proven only for `noisy-runner` (`plugins/noisy-tools-in-subagent/DESIGN.md`). The claim that a weak model fails silently on exploration is adopted without measurement |
| 2026-11-17 | Between two tiers, work whose error nobody would notice takes the stronger model; work with a check behind it keeps opus over fable. Open-ended research is fable | An exploration error nobody notices costs more than the model. Open-ended investigation moves from opus to fable, which costs more |
| 2026-11-17 | Reverses the two rows above: a subagent's model is picked by how much of the method the brief hands down. haiku runs a few named commands or extracts given text and never searches or reviews, sonnet carries a method spelled out with its check, opus is the default for any work a strong senior engineer does, research included, and fable is kept for deep theoretical work or where opus fell short | The maintainer: opus takes what a self-taught senior engineer could do, fable what needs one with deep theoretical grounding, and sonnet can do full data analysis given structure up front. Anthropic's measurements in `agentic-coding-handbook/sources/claude-platform/docs/optimizing-for-cost-and-intelligence.md` agree: on DeepResearch Bench II, Fable 5.2 cost 4.3 times as much as Sonnet for no measurable gain and scored below Opus; on a defect search, Opus with Sonnet subagents scored about the same as Opus alone for about a third less cost, while Haiku subagents dropped the F1 from 0.831 to 0.677. `choosing-a-model.md` moves to Fable only when Opus at `xhigh` still falls short |
| 2026-11-17 | The roles are `worker`, `task-subagent` and `resident-subagent`; the top-level session is a worker on one task | A dispatcher role that runs worker sessions is coming, and "orchestrator" does not tell the two session levels apart. Subagent roles say "subagent" so a session role and a subagent role cannot be confused |
| 2026-11-17 | `SessionStart` follows the cc-auth-switch role variables: silent when the role is in the system prompt, the launcher's file in mode `none`, `roles/<name>.md` for a bare role name, else the `default_role` option (`worker`) | The launcher config stays the one place that names a role's file, and a role in the system prompt survives compaction without a 10,000-character limit. Without a launcher the plugin behaves as before. cc-auth-switch reads the session role from the main checkout of this repository, while subagent roles and the hook's fallback come from the installed plugin; the two agree only once the checkout is pulled and the plugin updated to the same commit |
| 2026-11-17 | The plugin ships the `agent-roles:resident` agent type, mapped to the resident role; `resident_agent_types` stays for third-party types | `agent_type` is the only value the caller sets that reaches `SubagentStart` (2.1.325). Rejected: a role marker in the prompt rewritten by a `PreToolUse` hook on `Agent` (unverified that `updatedInput` can rewrite `prompt`, and the role would rest on a convention the model must remember), and pairing `PreToolUse` with the next `SubagentStart` by order (breaks when one message starts several agents) |
| 2026-11-17 | A session's crons survive its compaction, so a cron can revive a compacted session | Checked on Claude Code 2.1.325 in a throwaway session: a `* * * * *` cron that appended to a file fired at 17:16 and 17:17, `/compact` ran at 17:18:22, and the cron fired again at 17:18:27 and 17:19:28 with no input. Only manual `/compact` was checked, not auto-compaction. Crons live in the process: a restart or a resume loses them, and a recurring cron expires after 7 days |
| 2026-11-17 | A `dispatcher` role runs worker sessions in sibling tmux windows of its own tmux session and does no task work; every other session there is its worker, with another role or none | The human talks to one session per group of projects instead of managing each session. Ownership by tmux session needs no registration and adopts a session the human started by hand |
| 2026-11-17 | The dispatcher's memory is `.claude/dispatcher/roster.md` under its cwd, updated after every action that changes a worker's state | Only what is on disk survives compaction, and the file is also the human's view of what the dispatcher thinks is going on |
| 2026-11-17 | A compacted dispatcher is revived by its own cron, every 30 minutes while it has workers, not by a hook. The cron's pass compares the roster's creation date with `date -u`, creates the replacement before it deletes a cron over 6 days old, and creates one when `CronList` lacks it | Idle compaction never starts a turn. Crons survive compaction (see the 2026-11-17 check), but expire after 7 days and die with the process |
| 2026-11-17 | The dispatcher types into a worker's pane only at `prompt_empty` with the session idle, sends the Enter as a separate key, and checks the effect | A fast text-and-Enter arrives as one paste and the Enter becomes a newline; keys into a dialog or half-typed human input do damage. Slash commands such as `/compact` cannot travel in a message |
| 2026-11-17 | The dispatcher tells the human's input in a worker from its own by the transcript: its messages arrive as `<cross-session-message`, keystrokes it typed are in the roster. After the human's input it leaves the worker alone for 30 minutes | No CLI exposes cc-blackbox's `Prompt.origin` yet. The human stepping in must not be overridden by a nudge in the same minute |
| 2026-11-17 | An idle worker is nudged at 20 minutes. At 50 minutes the dispatcher retires it when nothing more is needed from it, and compacts it only when it must finish later; never at 2 hours | The prompt cache expires at 60 minutes, so a compaction after that pays for the whole context, and a worker that is about to be closed gains nothing from one |
| 2026-11-17 | A worker reports to a dispatcher only at milestones (plan ready, PR opened, blocked, done) and starts with a recap when the human steps in | The watch shows liveness, so a heartbeat would only cost turns |
| 2026-11-17 | GitHub PRs have no babysit skill; the dispatcher has the worker watch CI with `gh run watch` until one exists | `sdlc:mr-babysit` is built on `glab-watch` and only works for GitLab |
| 2026-11-17 | Reverses the row above: a worker babysits its MR or PR with `sdlc:mr-babysit`, on GitHub through `gh` | sdlc 0.23.2 states that `mr-babysit` and `mr-open` apply on GitHub, with `gh` doing the equivalent of `glab` |
| 2026-11-17 | The dispatcher answers only the dialogs and permission prompts it recognises and the human's authorization covers, by menu keys, and reads the screen again after. A denial a worker reports goes to the human; the dispatcher never runs it, answers it, or rewords it. It types the human's quoted words only when they cover the exact action and the worker refused the dispatcher's message, not the action | The role is the human's request to drive worker panes, which the session-watch skill otherwise forbids. Without these limits a dispatcher would launder a classifier's denial through a pane |
| 2026-11-17 | The brief names the task's definition of done, and the worker carries the task through it, rollout included: merge, release and install, or deploy, watch and `sdlc:wrap-up`. The dispatcher spot-checks a worker's claims before it passes them on, never merges, installs, releases or deploys, and retires the worker only after the task is done or dropped | The worker that made the change knows what to watch during its rollout. Work does not always end at the merge, and rollout steps such as a uv tool reinstall belong to one kind of project, not to the role |
| 2026-11-17 | A dispatcher is launched through cc-auth-switch | `list-active` reads a session's role from the cc-auth-switch start log; a session given only `FP_CC_AUTH_SWITCH_ROLE` shows no role, so a second dispatcher would be taken for a worker |
| 2026-11-17 | `FP_CC_AUTH_SWITCH_ROLE=none` injects no role on `SessionStart`, silently and before every other variable; the `default_role` option `none` means the same | `--agent-role none` set no variable, so the hook fell back to `default_role` and injected the worker role. A role name the plugin has no file for still warns, since that is a typo, while `none` is a request |
| 2026-11-18 | Every other session in the dispatcher's tmux session is managed, whoever started it, including permanent sessions for a topic that the human uses directly. A managed session with a task from the dispatcher in flight is working. One watch covers the whole tmux session, without session names. Every managed session is compacted after 50 minutes idle, the human's too, unless nothing happened since its last compaction. Nudges, waiting relays, claim checks and the cap of 3 apply to working sessions. The watch keeps every event: a session reports a summary of each turn the dispatcher's brief or message started, so the dispatcher does not read its transcript; at the end of a turn the human started, the dispatcher asks the idle session for a summary or reads the newest exchange, whichever is cheaper and more reliable (a message costs the human's conversation a turn and context, reading a long exchange costs the dispatcher tokens), notes what matters in the roster and acts on nothing else. The summary request is allowed during the 30-minute hands-off, being a question rather than a course change; the revive cron runs only while one is working and not every working session waits on the human. The dispatcher closes only a session it started, once its task is done, or one the human tells it to close; the roster records who started each session. Reverses the earlier rows that tie the revive cron and the cap to every worker and retire every worker after its task | The maintainer keeps permanent sessions in a dispatcher's tmux session (the `personal-life` session holds five), and one dispatcher kept its revive cron firing every 30 minutes all night for a single parked session. A watch filtered by tmux session picks up and drops sessions on its own, so no set needs maintaining; a watch given session names would have to be restarted whenever the set changed or a session restarted. The prompt cache expires at 60 minutes for any session, whoever uses it. The maintainer wants the dispatcher informed of what is discussed in the sessions he uses directly, so the watch is not filtered to membership and thresholds; a session working for the dispatcher is expected to report, one the human talks to is not. The cap is for the shared account limits, which an idle session does not use. A session the human started holds context the human chose to keep, so only the human closes it |
| 2026-11-18 | The dispatcher compacts an idle session only when it uses at least 15% of its context window, read from the `Ctx: <n>k (<p>%)` status line in `cc-session-tools inspect --screen` | The maintainer: under 15% a compaction makes the session dumber and saves little of the limits or money. A dispatcher compacted a worker at 99k tokens, about 10%. cc-session-tools 0.7.2 exposes no context-usage field: `inspect --json` has only cumulative token costs, so the share comes from the status line on the pane |
| 2026-11-18 | The revive cron's prompt ends with its creation date ("Created <UTC date>."), and the dispatcher reads the cron's age from the firing prompt or `CronList`; the roster keeps only the cron's id. Replaces the roster's creation date in the 2026-11-17 revive-cron row | The maintainer: the cron should say in its prompt when it was created. The date then travels with the cron itself, so a dispatcher whose roster lost or never had the date does not have to replace the cron to be sure of its age |

## How changes are checked

`make test` runs `hooks/test-inject-role.sh`, which feeds the hook payloads and environments and checks which role comes out, and fails when a role file exceeds 9,500 characters. The rules themselves have no eval suite: check a change to a role text by running a session that exercises the rule, and say in the commit that it was not measured when it was not.
