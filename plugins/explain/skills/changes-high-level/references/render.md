# Stage 4: render the page

You build the page from the deep dives' results. You write `page.json` and at most one diagram; `build.py` and the fixed template own all markup. You never write HTML or SVG. Budget: 2.5 minutes. Run `date +%s` when you start and again between steps; when 2.5 minutes have passed, build with what you have and report what is left.

Load `prose:technical-writing` before you write any prose field, and `diagrams:mermaid` before you write the architecture diagram. The structure of `page.json` is `scripts/page.schema.json` (one directory up from this file), and `scripts/fixtures/page.json` is a complete example.

The reader is a tech lead who reads many of these pages instead of the source. Contract changes must be complete; everything else is cut hard. Leave out every detail that does not change how the reader judges the change. The page's length follows the number of contract changes, not the size of the diff.

## 1. Merge the fragments

```bash
<build command> merge WORK/subdomain-*.json --checklist WORK/contract-files.json --code-tree <code tree> --base <REVIEW_BASE> --out WORK/contracts.json
```

Leave out `--code-tree` and `--base` when there is no code in reach or no diff.

- An `error` line names a fragment and a JSON path. Fix that fragment and run it again.
- A `conflict` line means two areas describe one object differently. Read the cited lines (a few reads at most), fix the wrong fragment, and merge again. Leave a conflict you cannot settle; the build keeps the first version.
- A `gap` line is a contract file no deep dive covered, or one left unknown. Do not hide it: the page shows it. Mention every gap in your reply.
- A `ref` line is a `path:line` that does not exist: a missing file, or a line past the end of the file. Find the right line with one `grep -n` in that file and fix the fragment, or remove the ref; never leave a ref that points nowhere.

## 2. Write `WORK/page.json`

The interface objects and packages come from `contracts.json`; do not copy them into `page.json`. `page.json` carries the headings and the short prose around them. The layout is the same on every page, top to bottom; a section without content is dropped, except the interfaces section and its four parts, which say "no change" when empty:

1. **Header** (`title`, `summary`, `state`, `size`, `generated`, `source`, `diff`, `ticket`). `summary` is one sentence. `state` is `implemented`, `proposed`, or `implemented and proposed`.
2. **Framing** (`framing`, required).
3. **Change map:** generated by the build from the fragments, never written by you: a services diagram when more than one service is involved, then one change-flow diagram per entry point. Every box links to its card.
4. **Interfaces:** a heading for the section and for each part that has objects; one sentence of `text` only where it adds what the objects do not show. The build draws the gaps, the summary table and the four parts (database, messaging, HTTP, other boundaries).
5. **Modules** (`modules`): `areas` with each area's deep-dive status (`deep dive`, `grouped`, `surface only`), `crossings` and `dependencies` from the notes, and the architecture diagram when three or more components are involved.
6. **Requirements:** only when `change.md` has acceptance criteria, each with where the change meets it, or "not in this change". A fact, not a verdict on completeness, and the heading too: "Where each acceptance criterion lands", never "All criteria are met".
7. **Concepts:** only when the source records terms, decisions, rejected alternatives or open points.
8. **Internals:** one flow per area at most, at most five steps, from the notes' `steps`. Cut steps that only restate the interfaces.
9. **Discussion:** who asked what and the answer, from `change.md`.
10. **Files:** with a diff, every changed file with its counts, from the numstat.

**Framing, last.** When every other section is written, write `framing`: one to three paragraphs that say what the change is and why it is being made (the problem, the reason, the approach and what it means for the service), so the reader knows what to look for below. It must not repeat the sections: no list of tables, queues, endpoints or packages. No bullets.

**Headings** state the finding ("The shipment request drops the item weight"), not the topic ("HTTP"); the build adds the topic label itself. Prose fields take a markdown subset: `` `code` ``, `**bold**` and `[text](https://...)`; everything else shows as text.

Every claim cites a `ref`. A claim whose `source` is `source text` in an implemented change is written as the source's claim ("the description says …"), never as a fact about the code. No invented rationale: when the source does not say why, say the reason is not recorded. Describe, never judge: "introduces the first direct call from `billing` to `customer`", never "this coupling is a problem".

## 3. Render the diagrams

`diagrams` in `page.json` lists every diagram the page shows, by `id`, with a `title` and an optional `caption`; the id is the file name in `WORK/diagrams/` (`<id>.mmd`, `<id>.svg`), and a section names its diagram by id. Pick them within the ceiling for the size class (tiny none, small one, medium three, large four): the deep dives' `<slug>-flow.mmd` files and your own `architecture.mmd`. At most one sequence diagram per flow that is really distinct; two sequence diagrams that differ in one message are one. Write `architecture.mmd` only when three or more components are involved, as a `flowchart` with the new parts marked "(new)" in their labels. Topology and payload diffs are page components, never Mermaid.

First write the generated diagrams; they do not count against the ceiling and are not listed in `page.json`:

```bash
<build command> diagrams WORK/contracts.json --out-dir WORK/diagrams
```

It prints the ids it wrote (`services`, `flow-…`, `database-er`). Then render those and every chosen diagram in one batch, each with a unique `-I` id (Mermaid scopes each SVG's CSS by it, so two inline SVGs with one id restyle each other), in the light theme the page shows diagrams in:

```bash
cd WORK/diagrams && n=0; for f in <ids>; do n=$((n+1)); mmdc -q -i "$f.mmd" -o "$f.svg" -t default -b transparent -I "explain-d$n" & done; wait
```

If the `noisy-tools-in-subagent:noisy-runner` agent type is available, hand this one command to a `noisy-runner` subagent and read its verdict. Otherwise run it yourself with the output redirected to `WORK/mmdc.log`, and read only the log's tail on failure.

A diagram that fails to parse: fix its `.mmd` and render only that one again, at most twice. If it still fails, mark it `"failed": true` in `page.json`; the page shows its source folded. When `mmdc` is not installed, skip this step: the build embeds the sources, and the page draws them from a pinned CDN import.

## 4. Build

```bash
<build command> page WORK/page.json --contracts WORK/contracts.json --diagrams-dir WORK/diagrams --code-tree <code tree> --base <REVIEW_BASE> --out <output path>
```

- `error` lines name a JSON path; fix `page.json` and build again, at most twice.
- A warning that a diagram is wider than the content column: for a `flowchart`, change its direction (`LR` to `TB`) or split it; for a `sequenceDiagram`, drop participants or shorten the messages, because it has no direction. Render that one again, and build again. A generated diagram is not edited; report its width.
- Other warnings (a section over its soft word limit, a flow over five steps, a missing cost or rollout label): fix the prose when it is quick; otherwise report them.

There is no visual review of the diagrams beyond the width check.

## Reply

The HTML path, the sections the build printed, every coverage gap, conflict and bad ref, the remaining warnings, and whether the diagrams were drawn by `mmdc` or need the CDN fallback.
